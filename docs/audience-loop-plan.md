## 1. 첫 소개 모드

### 현재 상태

이미 된 것:

- `bf63705`(9/25) 이후 판단 프롬프트에 "Introducing the project to new readers" 절이 붙는다(`src/core/prompts.ts` `INTRODUCTION_JUDGE`). 활성 채널 가운데 하나라도 게시 기록이 없으면 붙는다(`src/app/pipeline.ts` `buildPrompt`의 `anyUnannounced`).
- 첫 소개 초안은 변경 목록이 아니라 README·프로필을 근거로 쓴다. 기준선(README·프로필)이 있으면 다이제스트와 커밋·릴리스 수를 뺀다(`draftPrompt`의 `publicCandidate`, `draftCoverageGuide`). 10/22~10/24의 PR #75~#86이 이 경로를 계속 다듬었다.
- 숨김 기능: README가 실험·로컬 전용으로 표시한 기능은 `evidence.experimental`로 "지금 쓸 수 있다고 쓰지 말 것"으로 넘어간다. 프로필의 `avoid`("쓰지 않음")는 프롬프트와 lint(`avoid_terms`) 양쪽에 걸린다.

빠진 것:

1. **결정 규칙.** `applyResult`의 판단 반영은 첫 소개 여부와 관계없이 5개 항목(runnable·numbers·lesson·novelty·audience) 가중 합계를 6/4 기준에 댄다. 소개 절은 runnable·novelty·audience의 뜻만 바꾸고, numbers·lesson은 그대로 0~2를 받는다. 처음 알리는 프로젝트는 측정치나 실패담이 없어 보통 numbers·lesson이 0이다. 그러면 나머지 셋이 모두 2여야 겨우 6점이다. "2를 아껴 줘라"는 지시까지 있어서, 9/25의 4점 보류가 지금 코드에서도 그대로 재현될 구조다.
2. **변경 없음 → 묻기.** 다이제스트가 알릴 변경을 하나도 찾지 못하면 점수와 관계없이 `ask`가 된다. 첫 소개는 변경이 아니라 프로젝트 자체가 글감이므로 이 규칙이 맞지 않는다.
3. **숨김 기능 칸.** `avoid`는 회사명·내부 호스트명 같은 "말"을 위한 칸이고 생성기도 그렇게 채운다. "운영에서 꺼 둔 기능"은 README에 버젓이 적혀 있고 실험 표시도 없는 경우가 많다(9/25 사례). 지금은 이를 적을 자리가 없어서, 사용자가 `avoid`에 기능 이름을 넣는 우회만 가능하다.

### 바꿀 것

- 판단 결정: 그 저장소에 **어느 채널에도 게시 기록이 없으면** 첫 소개 판단으로 본다. 첫 소개 판단의 합계는 runnable·novelty·audience 세 항목만으로 10점 만점 환산한다(가중치 유지). numbers·lesson 점수는 기록하되 결정에 쓰지 않는다. 기준점(6/4)은 그대로 둔다.
  - 이미 한 채널이라도 게시한 저장소는 지금처럼 5개 항목으로 결정한다. 채널별 소개 초안 여부(`requestedIntroduction`)는 지금 규칙을 유지한다.
  - 같은 저장소의 다른 글감에 버리지 않은 첫 소개 초안이 이미 있으면 첫 소개 판단을 다시 적용하지 않는다. 릴리스마다 소개 초안이 쌓이지 않게 하려는 것이다.
- 첫 소개 판단에서는 "변경 없음 → 묻기"를 적용하지 않는다.
- 판단 결과에 첫 소개 판단이었다는 표시를 남긴다(`judgments.purpose`, 마이그레이션 0019). 화면의 판단 설명에 "아직 알린 적 없는 프로젝트라 소개 기준으로 판단했습니다"를 붙인다.
- 프로필에 `unreleased: string[]`("공개하지 않은 기능")을 둔다. 사용자가 직접 적는 칸이며 모델이 채우지 않는다. 프로필 JSON 컬럼이라 마이그레이션은 필요 없다.
  - 프롬프트: 프로필 블록에 "아직 공개하지 않은 기능: 언급·암시·홍보하지 말 것. README에 있어도 마찬가지"를 넣는다.
  - lint: `unreleased_feature` 규칙. 본문에 항목 문자열이 있으면 실패다. 자동 보정 대상에 넣고, 문체 예시 승격도 막는다.
  - 화면: 프로필 편집에 칸을 추가한다(쉼표 구분, 짧은 기능 이름을 권장).

### 완료 조건

- 게시 기록이 없는 저장소에서 runnable 1·novelty 2·audience 1, numbers 0·lesson 0이면 결정이 `draft`다. 같은 점수라도 게시 기록이 있으면 지금처럼 `defer`다(테스트).
- 다이제스트가 변경을 못 찾아도 첫 소개 판단이면 `ask`로 떨어지지 않는다(테스트).
- 다른 글감에 살아 있는 소개 초안이 있으면 첫 소개 판단을 적용하지 않는다(테스트).
- 프로필의 공개하지 않은 기능이 프롬프트에 들어가고, 본문에 쓰이면 `unreleased_feature`가 실패한다(테스트).
- 실제 생성(C)에서 Tend 소개 초안이 변경 목록 없이 README·프로필 근거로 나온다. 이것은 사람이 읽고 판단한다.

### 예상 크기

중. pipeline·prompts·lint·profiles·schema(마이그레이션 1개)·ProfileBlock·i18n·테스트. 300~500줄.

### 현재 상태

있는 것: 금지어(`소개합니다`·`드디어`·🚀 등), 이모지 글머리, 해요체로 지정된 채널의 합니다체 종결(`register_mismatch`), 작성자 역할(`만들었습니다`·`I built`), 근거 없는 평가·추천(`정말 편해요`·`꼭 추천`), 최상급 주장. 대부분 자동 보정(`REPAIRABLE`) 대상이다.

| 사례 | 지금 | 이유 |
|---|---|---|
| 콜론으로 시작하는 첫 줄(`Tend: …`, `소개: …`) | 검사 없음 | |

| 자기 홍보 말투(`지금 바로 써 보세요`, `놓치지 마세요`, `check it out`) | 일부만 | 평가 표현만 잡고 행동 촉구 문구는 안 잡는다 |

### 바꿀 것

한국어 본문(한글 포함)에 다음 규칙을 더한다. 영어 대응 표현이 분명한 것은 영어 본문에도 건다.

| 규칙 | 대상 채널 | 판정 | 보정 | 예시 승격 차단 |
|---|---|---|---|---|
| `colon_opening` | X·Threads·LinkedIn·사용자 채널 | 첫 줄이 `:`로 시작하거나, 첫 줄이 30자 이하의 머리말 + `:`로 시작 | O | O |
| `feature_list` | X·Threads·LinkedIn | `-`·`*`·`•`로 시작하는 줄이 2개 이상 | O | O |
| `self_promotion` | 전체(Show HN·GN 포함) | 행동 촉구·과장 문구 목록(`지금 바로`, `꼭 써 보세요`, `놓치지 마세요`, `한번 써 보세요`, `많은 관심`, `check it out`, `give it a try`, `don't miss` 등) | O | O |
| `register_mixed` | 한국어 전체(해요체 채널은 기존 `register_mismatch`가 맡으므로 제외) | 인용·코드를 뺀 서술문 종결에 `ㅂ니다`와 `요`가 함께 있음 | O | O |
| `first_person_need_review` | 전체 | `써 보니`, `써보니`, `사용해 보니`, `팔다 보니`, `쓰다 보니`, `해 보니`, `제가 직접`, `I tried`, `I've been using`, `in my experience` 등. 같은 문장이 근거(README·프로필 `why`)에 있거나 편집 지시가 경험을 요청하면 통과 | O(생성 초안만) | O |

`first_person_need_review`는 "확인 필요" 경고다. 사용자가 직접 고쳐 쓴 글에 실제 경험을 넣으면 경고만 보이고 저장·복사는 그대로 된다. 생성 초안에서는 자동 보정이 그 문장을 지운다. 작성자 역할 검사와 같은 방식이다.

화면에는 규칙 이름 대신 읽히는 이름을 붙인다(`ui.tsx`, `en.ts`).

### 완료 조건

- 각 규칙에 걸리는 예와 걸리지 않는 예를 단위 테스트로 둔다. 걸리지 않는 예에는 URL 안의 콜론, Show GN 절의 목록, 인용문 안의 합니다체, 근거에 있는 경험 문장을 넣는다.
- 다섯 규칙이 `REPAIRABLE`과 `EXAMPLE_GATE`에 들어간다(테스트).
- 11/12 Threads 원고와 비슷한 합성 본문을 넣으면 다섯 규칙이 모두 걸리고, 고친 본문은 모두 통과한다(테스트).
- 기존 테스트가 모두 통과한다. 기존 생성 표본(`docs/generation/*.json`)에서 오탐이 늘었는지는 C 단계에서 실제 초안으로 확인한다.

## 3. 게시 마지막 단계

### 현재 상태

- 초안 화면에 "{채널} 작성 화면 열기" 버튼이 있다. X는 `https://x.com/compose/post`, Threads는 `https://www.threads.net/` 홈으로 간다. 본문은 채워지지 않는다.
- 게시 뒤 URL을 붙여 넣으면 발행 기록이 생기고, 채널과 다른 호스트는 거부한다(9/30 보완).
- 주간 Discord 요약이 "복사만 하고 게시 기록이 없는 글 N개"를 알린다. Discord를 연결하지 않았으면 알림이 없다.
- 실제 자동 게시는 범위 밖이다(유지).

### 바꿀 것

- X는 `https://x.com/intent/post?text=…`, Threads는 `https://www.threads.net/intent/post?text=…`로 본문을 채운 작성 화면을 연다. 버튼을 누르면 복사 기록(`copied_at`)도 남긴다. 링크를 연다고 게시한 것은 아니므로 발행 기록은 만들지 않는다.
- 작성 화면을 연 뒤 돌아오면 URL 입력란을 바로 펼친다.
- 앱 안의 미게시 표시: 사이드바에 "복사했지만 링크가 없는 글 N개"를 띄운다. Discord가 없어도 보이게 한다.

### 완료 조건

- X·Threads 초안에서 버튼이 본문(줄바꿈·URL 포함)을 채운 작성 화면을 연다. 브라우저에서 확인한다(게시는 하지 않는다).
- 링크 열기는 복사 기록을 남기고 발행 기록은 남기지 않는다(테스트).
- 미게시 글이 있으면 사이드바에 개수가 보이고, 누르면 해당 초안으로 간다.

### 예상 크기

소. channels·DraftPanel·사이드바·테스트. 100~200줄.

## 4. 연재 계획

### 현재 상태

없다. 모든 글감은 릴리스·PR 묶음 단위이고, "이번 주 한 편"(`weekly-pick.ts`)이 그중 하나를 고른다. 새 릴리스가 없으면 쓸 글이 없다는 결론만 나온다. Tend처럼 수요가 있는데 릴리스 단위로는 할 말이 적은 제품에서 이 점이 가장 크게 막힌다.

### 바꿀 것

- 프로젝트(저장소) 화면에 "2주 연재 계획" 기능을 둔다. 입력은 프로필·README·최근 릴리스·게시 기록이다. 출력은 5편 순서(소개 → 사용 장면 → 동작 원리 → 겪은 문제 → 시연)와 각 편의 각도, 근거 위치, 권장 채널, 권장 날짜다.
- 각 편은 글감(`candidates.type = "series"`)으로 만든다. 판단을 건너뛰고 사용자가 고른 편만 초안을 만든다. 근거가 없는 편(예: 겪은 문제의 기록이 없음)은 "근거 필요"로 표시하고, 지어내지 않는다.
- 이미 게시한 편은 다음 편 초안에 "이전 편에서 말한 것"으로 넘겨 반복을 막는다.

### 완료 조건

- Tend로 계획을 만들면 5편 각각에 근거 위치가 있고, 근거 없는 편은 "근거 필요"로 표시된다.
- 계획의 한 편을 고르면 그 각도로 초안이 만들어지고, 앞 편의 게시 내용을 반복하지 않는다(사람 검토).
- 계획 생성은 사용자 요청으로만 실행한다(자동 쿼터를 쓰지 않음).

### 예상 크기

대. 새 프롬프트·스키마(후보 유형 추가와 계획 테이블)·API·화면·테스트. 600줄 이상. 1·2번 결과를 본 뒤 설계를 다시 확인하는 것이 좋다.

## 5. 성과 되먹임

### 현재 상태

- 발행 기록마다 수동 반응(좋아요·댓글·리포스트·방문·설치·가입)을 입력할 수 있고, 일부 채널은 자동으로 반응을 가져온다(`reactions.ts`).
- 스타 7일 변화(기준 추세 대비)를 채널별로 묶어, 표본이 2개 이상이면 판단 프롬프트에 넘긴다(`channelResultsForJudge`).
- 없는 것: 조회수(노출) 입력 칸. 성과를 **문체 예시 선택**에 반영하지 않는다. `examplesFor`는 최신순이다.

### 바꿀 것

- `PublicationStats`에 `views`를 추가하고 수동 입력 칸을 둔다.
- 문체 예시 선택: 작성자 글(authored)이 3개를 넘으면, 같은 채널에서 반응률(좋아요+리포스트 ÷ 조회, 조회가 없으면 좋아요)이 높은 글을 하나 넣는다. 나머지는 최신순을 유지한다. 표본이 작으므로 "성과가 좋았던 글" 표시만 붙이고 가중치는 두지 않는다.
- 판단에는 지금의 스타 기반 줄에 조회·클릭 평균을 더한다(표본 2개 이상일 때만).

### 완료 조건

- 조회수를 입력·수정할 수 있고 발행 화면에 보인다.
- 반응 기록이 있는 작성자 글이 예시 목록에 들어간다(테스트).
- 표본이 1개면 판단 프롬프트에 성과 줄이 붙지 않는다(테스트).

### 예상 크기

소~중. types·publications·pipeline·Published 화면·테스트. 150~250줄.
