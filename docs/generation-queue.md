# 생성 요청·진행 상태 개선 — 2026-09-22

## 결과

공개 Vite 자료로 X 영어와 Threads 한국어를 실제 Gemini 생성 경로에 요청했다. 두 채널의 접수 응답은 로컬 측정에서 **34ms**, 생성 완료는 **61.1초**였다. 생성 시간이 짧아졌다는 뜻이 아니라, 모델을 기다리는 동안 HTTP 요청을 붙잡지 않게 한 것이다. 같은 요청을 바로 다시 보내도 작업 ID는 `[1, 2]`로 같았고 최종 초안도 채널별 하나씩 생성됐다.

[실행 기록·생성문](generation/queue/live-results.json) · [실패 화면](generation/queue/failed-mobile.png)

## 구현

[Microsoft의 비동기 요청·응답 패턴](https://learn.microsoft.com/en-us/azure/architecture/patterns/asynchronous-request-reply)을 참고해 다음 흐름을 적용했다.

1. 판단·재분석·다시 쓰기 요청을 기존 SQLite `llm_jobs`에 저장하고 `202 Accepted`를 반환한다. `Location`은 상태 조회 주소, `Retry-After: 5`는 조회 간격이다.
2. 서버 시작 시 워커가 모델 API 작업을 처리한다. 프로세스당 한 작업씩 실행해 무료 키 요청이 한꺼번에 몰리지 않게 했다. 기존 CLI 워커는 로컬 작업만 가져간다.
3. 작업과 결과, 다음 단계 큐 생성을 트랜잭션으로 반영한다. 작업 점유 토큰으로 만료된 워커의 늦은 완료 요청을 거절한다.
4. 화면은 대기·진행·완료·실패를 구분하고 실패 작업을 다시 요청할 수 있다. SSE와 5초 간격 상태 조회를 함께 사용하며, 새로고침 후에도 DB 상태를 복원한다. 상태 API에는 프롬프트·원본 모델 응답·점유 토큰을 포함하지 않는다.
5. 새 글감의 수동 초안 요청은 요약 완료 후 지정한 채널·언어·수정 지침으로 이어진다. 같은 흐름에서 자동 판단·자동 초안까지 중복 실행하지 않는다. 요약 근거가 없으면 실패 이유를 남기고 멈춘다.
6. 동일한 진행 중 요청은 재사용하고, 다른 지침으로 덮어쓰려는 요청에는 `409`를 반환한다. 재시도는 원래 작업의 프롬프트·수정 지침을 보존한다.
7. 모델 호출과 재시도 전체에 3분 제한을 적용한다. 서버 종료 시 진행 중 네트워크 요청을 중단하고 실패를 기록한다. 저장된 작업은 재시작 후 다시 조회할 수 있다.

서버 워커도 기존 완료 처리기의 결과 형식 검증을 거친다. 실패 내용은 자격 증명이 포함될 수 있는 제공자 응답 원문 대신 상태 코드와 복구 안내로 저장한다. 생성 중 글감이 삭제·보관·발행됐다면 늦은 결과로 이를 되살리지 않는다.

## 검증

전체 21개 테스트 파일의 **95개 테스트**, 린트·타입 검사·프로덕션 빌드·`git diff --check`가 통과했다.

- 실제 Gemini 두 채널 생성: 202 접수 → 대기 → 진행 → 완료, 각 채널 초안 한 개.
- 실제 HTTP API와 브라우저: 진행 중, 완료, 의도적으로 구성한 키 미설정 실패 상태를 각각 1440px·390px에서 확인했다. 총 여섯 화면 조합에서 가로 넘침·실행 오류·axe WCAG 2 A/AA 및 2.1 AA 탐지 위반 0. 새로고침 전후 상태도 동일했다. 실제 계정·운영 DB는 사용하지 않았다.
- 실패 화면에서 발견한 배지 색 대비를 보완했다. [진행](generation/queue/running-browser.json), [완료](generation/queue/completed-browser.json), [실패](generation/queue/failed-browser.json) 검사 기록.
- 회귀 테스트: 빠른 접수와 중복 요청, 소유자 격리, 안전한 상태 응답, 실패·재시도 지침 보존, 선행 요약과 지정 채널 연결, 근거 없음·잘못된 모델 응답, 점유 만료·늦은 완료, 서버/CLI 작업 분리, DB 재개방 후 복구, 보관 중 완료 무시, 자동 처리 충돌 격리, 네트워크 중단, 화면 폴링·재시도·로컬 워커 안내.

## 적용과 한계

- `0008_server-generation-queue.sql`은 기존 작업 테이블에 실행 주체와 후속 생성 계획 두 컬럼을 추가한다. 기존 행은 로컬 워커 작업으로 유지된다. 빈 DB 생성과 구버전 DB의 데이터 보존·재실행·스냅샷 일치를 검사했다.
- 일반 서버 시작 시 마이그레이션과 서버 워커가 함께 시작된다. 이번 작업에서 운영 DB 마이그레이션이나 배포를 실행하지 않았다.
- 모델 자체의 응답 시간과 무료 키 한도는 그대로다. 작업이 많으면 큐에서 기다린다. 34ms는 로컬 단일 측정이며 서비스 전체의 성능 보장은 아니다.
- 강제 종료된 진행 작업은 기존 10분 점유 기한이 만료된 뒤 회수되며, 자동 점유는 작업당 최대 3회다. 결과 반영 중복은 막지만, 장애 시 외부 모델 호출 비용까지 정확히 한 번으로 보장하지는 않는다.
- 재시도는 기존 프롬프트를 사용한다. 변경 자료를 새로 반영하려면 다시 분석하기를 사용한다. 모델 설정은 실행 시점의 값을 사용한다.
